# Process overview

## From the brief to Serumah

The brief asked for a multi-user, real-time website that's good. For Crit 8, I made a kitchen tracker, chosen partly because it suited the real-time part of the brief, but what my house actually gets confused about is money. My tutor said my other idea was more complete: Serumah, a Telegram bot my housemate made, which we already use to split grocery bills, track who owes who and rotate chores. So for Crit 9, I rebuilt the app as Serumah, for my house of five, who shop on different days with different people. Good here means nobody is confused about who to pay, and nobody has to chase or nag anyone, because we trust each other. I built bills first, because debts are what get confusing; chores aren't built yet because of time.

## Where I stand on "good"

I read Robin Sloan's ["An app can be a home-cooked meal"](https://www.robinsloan.com/notes/home-cooked-app/). What I took from it is that an app can be made for one small group, by someone who knows them. Serumah is built for my house only: no accounts, and only what we need, because we trust each other. [Splitwise](https://www.splitwise.com/) is built for any group, with accounts, simplified debts and reminders. I left those out: accounts aren't needed when we trust each other, simplifying debts means paying someone without knowing why, and reminders nag. But trust only decides what I leave out, not how careful the money is: only the person paid can say a payment never arrived, only the payer can delete a bill, and every split adds up to the cent.

## Stack

I kept the stack as small as the house: one Node and TypeScript server, SQLite on the Fly volume, and pages built on the server with no framework. The machine is small and the app is for one house, so one process and one file are enough; the cost is more hand-written HTML, including escaping everything people type. Live updates use server-sent events rather than WebSockets, because the server only needs to tell open pages that something changed, and each page then fetches itself again. Every button is an ordinary form, so the app still works without JavaScript, and the server always works the money out itself instead of trusting the page. For receipts I chose Anthropic's official SDK over plain HTTP for its retries and typed errors, which the "reading isn't available" fallback relies on; the agent pinned a release over two weeks old ([`d67d2a0`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/d67d2a0)).

## How I worked with the agent

I brainstormed with the agent: it asked me one question at a time, and I made each decision. For receipts, I asked whether to train my own model; the agent said it would read worse in the time left, so I chose Claude Haiku. Each decision is written into a design before anything is built ([`35694f8`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/35694f8), [`338f74a`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/338f74a)); I reread it first, then either redesign or let it build. I also redesigned several times after building. Every design is checked against the rules in `CLAUDE.md`. When a decision broke a rule, like my idea of a password for receipts, I either changed the decision or rewrote the rule, and the new rule went in before any code. Each rule that matters also has a check in `spec/`, written to fail first, which the app has to pass from then on. I'm not good at visual design, and the agent is, so I let it propose and I choose. When it built a new screen before showing me, I asked it to show me designs first. After that, it made pages of mockups I could tap through, I picked what I preferred, and I tried each one on my phone before it went live; that is how the receipt screens and the app's colours were chosen. I work this way because it's faster to get a feature right in one go than to rebuild it, and because I keep control: I know what happened at each step and feel connected to each part, instead of overseeing everything at once.

## What I decided, and threw away

Payments first waited until the person paid tapped "Got it". I switched to counting them at once, because in a busy week everyone would wait on each other, and our Serumah bot already counts them straight away ([`5e7789e`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/5e7789e), [decision record](docs/decisions/0001-payments-count-at-once.md)). For telling people apart, I went from no PIN to a 4-digit PIN per name, like Netflix profiles in one household, and turned down the agent's idea that housemates reset each other's PINs, because asking a housemate brings back the awkwardness. Splitting a receipt went through three versions: an equal split with the items listed ([`d67d2a0`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/d67d2a0)), a tick for every person on every line, which made a long receipt very long ([`93a44d6`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/93a44d6)), and person by person, where I pick a face and tap the lines they had ([`ff0d154`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/ff0d154)). Lines first started ticked for everyone; I made them start with nobody. Reading receipts was first limited to a list of houses. I opened it to every house, so a marker doesn't need a code from me, with a daily limit, a spend cap, and typing by hand when Claude can't be reached ([`1a8dc43`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/1a8dc43)).

## Where the work was corrected

When the agent got something wrong, the fix went into a check or a rule, not a retry. A double tap on "Delete" showed an error even though the first tap counted; a failing check came first, then the fix ([`a415af7`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/a415af7)). Chrome offered one person's PIN on another person's page, so the PIN box stopped being a password field, with a check for it ([`e3315bc`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/e3315bc)). When I asked the agent to write my README, it refused, pointing to my own rule that the README is my writing ([`488b1b1`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/488b1b1)). After a receipt scan, the page stopped updating live; the agent confirmed the cause in Chrome, wrote a check that failed, then made a one-line fix ([`ff0d154`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-fiardiel/commit/ff0d154)).

## How I knew it was right

Before accepting a change, `pnpm check` ran about 200 checks against the running app, including ones that the page shows the same numbers the server saves. Haiku was tested on made-up receipts with a promo, a surcharge and GST before I relied on it, then on my real Chemist Warehouse receipt. After each deploy the live site was checked, and I judged the house page with my phone at arm's length.
